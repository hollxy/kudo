上下文工程如何助你的公司摆脱 AI 代码泛滥之困：来自 Qodo 和 Monday.com 的经验

Carl Franzen

随着云端项目追踪软件 monday.com 的工程组织规模扩大到 500 多名开发者，团队开始感受到成功带来的压力。产品线日益增多，微服务激增，代码提交的速度已经超过了人工审查所能跟上的节奏。公司需要一种方法来审查每月数千个拉取请求，既不能让开发者陷入繁琐工作的泥潭，也不能让质量下滑。

就在那时，研发副总裁兼 Growth 和 monday Dev 团队负责人 Guy Regev 开始尝试一款来自 Qodo 的新 AI 工具，Qodo 是一家专注于 AI 智能体的以色列初创公司。正如 Qodo 和 monday.com 今日联合发布的一份新案例研究所揭示的，这次最初只是轻量级的测试，很快就成为了 monday.com 软件交付基础设施的关键组成部分。

“Qodo 感觉不像又一个工具——它更像是为团队增添了一位真正了解我们工作方式的新成员，” Regev 在最近一次视频采访中告诉 VentureBeat，并补充说它“每月阻止了超过 800 个问题流入生产环境——其中一些本可能导致严重的安全漏洞。”

与 GitHub Copilot 或 Cursor 这类代码生成工具不同，Qodo 并不试图编写新代码。相反，它专注于代码审查——利用其所谓的上下文工程来理解拉取请求中不仅改变了什么，还理解为何改变、如何与业务逻辑保持一致，以及是否遵循了内部最佳实践。

“你可以调用 Claude Code 或 Cursor，五分钟内生成 1000 行代码，” Qodo 的联合创始人兼 CEO Itamar Friedman 在与 Regev 同一次的视频采访中说，“但你只有 40 分钟，根本审查不完。所以，你需要 Qodo 来帮你做审查。”

对于 monday.com 来说，这项能力不仅仅是有帮助——它是变革性的。

规模化代码审查

在任何一个时间点，monday.com 的开发者都在数百个代码库和服务中发布更新。工程组织在紧密协作的团队中工作，每个团队分别对齐产品的特定模块：市场营销、CRM、开发工具、内部平台等等。

这正是 Qodo 发挥作用的地方。该公司的平台利用 AI 不仅检查明显的错误或风格违规，还评估拉取请求是否遵循团队特定的规范、架构指南和历史模式。

它通过学习你自己的代码库来实现这一点——通过学习以往的 PR、评论、合并记录，甚至 Slack 对话来理解你的团队如何工作。

“Qodo 给出的评论并非泛泛之谈——它们反映了我们的价值观、我们使用的库，甚至我们对功能开关和隐私等事务的标准，” Regev 说。“它具备上下文感知能力，这是传统工具所不具备的。”

“上下文工程”究竟意味着什么

Qodo 将其独家秘诀称为上下文工程——这是一种系统级方法，用于管理模型在做决策时能看到的一切信息。

这当然包括 PR 的代码差异，但也包括此前的讨论、相关文档、代码库中的相关文件，甚至测试结果和配置数据。

这个想法是，大语言模型并不真正“思考”——它们根据给定的输入预测下一个 token。因此，它们输出的质量几乎完全取决于输入内容的质量和结构。

正如 Qodo 的社区经理 Dana Fine 在一篇博客文章中所说：“你不仅仅是在写提示词，你是在固定的 token 限制下设计结构化的输入。每一个 token，都是一个设计决策。”

这不只是理论。在 monday.com 的案例中，这意味着 Qodo 不仅能发现明显的错误，还能发现那些通常会逃过人工审查的细微问题——硬编码变量、缺失的回退机制，或是违反跨团队架构约定的情况。

有一个例子很突出。在最近的一个 PR 中，Qodo 标记了一行无意中暴露了一个预发布环境变量的代码——这是任何人工审查者都没有发现的。如果它被合并，可能会在生产环境中引发问题。

“我们修复这个安全漏洞以及它可能引发的法律问题所花费的时间，将远远超过我们从单个 PR 审查中节省下来的时间，” Regev 说。

集成到开发流程中

如今，Qodo 已深度集成到 monday.com 的开发工作流中，分析拉取请求，并根据以往的团队代码审查提供具备上下文感知的建议。

“它感觉不像又一个工具……它感觉像另一位加入系统的队友——一位会学习我们工作方式的队友，” Regev 指出。

开发者在审查过程中会收到建议，并保留对最终决策的控制权——这种“人机协同”模式对于工具的推广至关重要。

由于 Qodo 通过拉取请求操作和评论直接集成到 GitHub，Monday.com 的基础设施团队没有面临陡峭的学习曲线。

“它只是一个 GitHub action，” Regev 说。“它会创建一个包含测试的 PR。它不像一个我们必须学习的独立工具。”

“其目的实际上是帮助开发者学习代码、承担责任、相互给予反馈，并从中学习、确立标准，” Friedman 补充道。

成果：节省时间，预防错误

自更广泛地推行 Qodo 以来，monday.com 在多个团队中都看到了可衡量的改进。

内部分析显示，开发者平均每个 PR 大约能节省一个小时。将这个数字乘以每月数千个 PR，节省的时间很快就能达到每年数千个开发者小时。

这些不仅仅是表面问题——许多都与业务逻辑、安全性或运行时稳定性有关。而且因为 Qodo 的建议反映了 monday.com 的实际约定，开发者更有可能采纳它们。

系统的准确性根植于其以数据为先的设计。Qodo 基于每个公司的私有代码库和历史数据进行训练，以适应不同的团队风格和实践。它不依赖于一刀切的规则或外部数据集。一切都是量身定制的。

从内部工具到产品愿景

Regev 的团队对 Qodo 的影响印象深刻，他们已经开始规划 Qodo 与 Monday Dev（monday.com 正在构建的面向开发者的产品线）之间的更深度的集成。

其愿景是创建一个工作流，让业务上下文——任务、工单、客户反馈——能直接流入代码审查层。这样，审查者不仅可以评估代码是否“能用”，还可以评估它是否解决了正确的问题。

“以前，我们有 linter、danger 规则、静态分析……都是基于规则的……你需要去配置所有规则，” Regev 说。“但它无法察觉你未曾意识到的问题……Qodo……感觉它正在从我们的工程师那里学习。”

这与 Qodo 自身的产品路线图高度契合。该公司不仅审查代码，它正在构建一个完整的 AI 智能体平台——包括用于上下文感知代码生成的 Qodo Gen、用于自动化 PR 分析的 Qodo Merge，以及 Qodo Cover，这是一个利用运行时验证来确保测试覆盖率的回归测试智能体。

所有这些都由 Qodo 自有的基础设施驱动，包括其新的开源嵌入模型 Qodo-Embed-1-1.5B，该模型在代码检索基准测试中，其表现超越了 OpenAI 和 Salesforce 提供的模型。

下一步是什么？

Qodo 目前正以免费增值模式提供其平台——对个人免费，通过 Google Cloud 的 Perks 计划为初创公司提供折扣，并为需要 SSO（单点登录）、气隙部署或高级控制功能的公司提供企业级服务。

该公司已经与 NVIDIA、Intuit 和其他财富 500 强公司的团队合作。得益于最近与 Google Cloud 的合作关系，Qodo 的模型可直接在 Vertex AI 的 Model Garden 中使用，这使其更容易集成到企业流程中。

“上下文引擎将成为 2026 年的重头戏，” Friedman 说。“如果企业想要真正理解并帮助他们的人工智能，就需要构建自己的‘第二大脑’。”

随着 AI 系统在软件开发中变得越来越根深蒂固，像 Qodo 这样的工具正在向我们展示，在恰当的时机提供正确的上下文，将如何变革团队在整个企业范围内构建、交付和扩展代码的方式。
